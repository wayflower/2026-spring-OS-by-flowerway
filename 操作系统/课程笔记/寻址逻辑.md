SATP在不同的进程之间是不一样的，它存储了真正的物理地址，以便MMU在不同的进程中进行虚拟->物理的转换过程。

而在每个进程中，所有给进程/cpu看的地址都是虚拟地址，只有在真正用到，比如说pc指向这条指令，然后取指过程中，把pc的虚拟地址转化为物理地址，硬件从对应的物理地址处把指令取回来。

栈指针寄存器在cpu中只有一个，但一个进程有两个栈，用户和内核栈，在权限切换时，这个栈指针会改变指向（这是软件做的）。

pc也只有一个，在切换权限时，硬件将用户态的pc保存在trapframe中，随后在trampoline.s里，软件把其他的寄存器也保存在trapframe中。

接下来进行内核态的代码（这部分代码存储在内核态的那部分虚存中，这部分内容是所有进程的内核态共享的）。

执行到需要调度时，内核执行一个swtch，将一部分寄存器的内容存到这个进程的pcb下的context里，而由于调用了call，会将准备返回（也就是调度回来以后下一条该执行的指令）的指令存入ra，在汇编代码中将ra也一并存入context，然后交出栈指针和pc，给另一个进程的内核使用，另一个进程的内核态从它的pcb里读出context并填入相应的寄存器，恢复上下文并开始继续运行。

- RISC-V指令集双进程调度与寻址：
    
    **🌍 世界观设定（初始状态）**
    在这个系统中，只有一条真实的 8GB 物理内存条（RAM）。但有两个进程，它们各自拥有独立的 4GB 虚拟地址空间。
    • **物理内存 (RAM)**：真实宇宙。
    • **Process A (PID 5)**：正在执行 `read(fd, 0x4000, 4096)`，试图把文件读到虚拟地址 `0x4000`。
        ◦ 它的页表基址寄存器（SATP）指向物理页：`0x80001000`。
        ◦ 它的内核栈（kstack）物理地址：`0x1000A000`。
    • **Process B (PID 6)**：即将执行 `mmap(NULL, 4096, PROT_READ|PROT_WRITE, MAP_SHARED, fd, 0)`，目标是映射到虚拟地址 `0x6000`。
        ◦ 它的页表基址寄存器（SATP）指向物理页：`0x80002000`。
        ◦ 它的内核栈（kstack）物理地址：`0x1000B000`。
    
    ---
    
    **🎬 第一幕：Process A 的真实寻址（系统调用执行中）**
    **1. 陷入内核**：
    A 执行了 `read` 的 `ecall` 指令。硬件将特权级切为内核态，A 的 32 个用户寄存器被汇编代码压入 A 的 `trapframe` 中。CPU 栈指针（SP）切换到 A 的内核栈 `0x1000A000`。
    **2. MMU 的翻译（内核态写数据）**：
    内核拿到了用户传进来的目标虚拟地址 `0x4000`。内核调动磁盘控制器，准备把 4KB 的文件数据写进去。
    此时，MMU（内存管理单元）介入，开始查 Process A 的页表（根据 SATP = `0x80001000`）：
    • MMU 提取虚拟地址 `0x4000` 的虚拟页号（VPN）：`0x04`。
    • MMU 在 A 的页表中查找第 `0x04` 项，发现对应的物理页帧号（PFN）是 `0x2F00`，且权限合法（PTE_V | PTE_W | PTE_U = 1）。
    • MMU 将 PFN 和偏移量结合，生成真实**物理地址：`0x02F00000`**。
    • 磁盘 DMA 将文件数据疯狂灌入物理内存条的 `0x02F00000` 处。进程 A 毫不知情，它以为数据进到了 `0x4000`。
    **🎬 第二幕：时钟中断与夺舍（上下文切换）**
    **3. 时钟滴答（Timer Interrupt）**：
    突然！主板上的时钟芯片发出硬中断。正在 A 的内核栈里干活的 CPU 被强行打断。内核意识到：A 的时间片用完了。
    **4. 封存 A 的进度（保存 Context）**：
    内核调用 `yield()` $\rightarrow$ `sched()` $\rightarrow$ `swtch()`。
    `swtch` 汇编函数把 CPU 当前的内核寄存器（比如 `ra` 返回地址、当前的内核栈指针 `sp = 0x1000A800`）保存到 A 的 PCB 档案袋中，即 `proc[5].context`。
    **5. 唤醒 B 的进度（恢复 Context）**：
    调度器（Scheduler）在 PCB 数组中选中了 RUNNABLE 状态的 Process B (PID=6)。
    `swtch` 函数从 `proc[6].context` 中抽出 B 上次休眠时保留的内核寄存器，强行覆盖到 CPU 硬件寄存器上。
    *最核心的一步*：内核执行一条特殊指令（向 SATP 寄存器写入 `0x80002000`），**瞬间切换了 MMU 的翻译字典！** 从这一刻起，CPU 眼中的整个虚拟空间变成了 B 的宇宙。
    **🎬 第三幕：Process B 的“画饼”与“填坑”（mmap 全过程）**
    **6. B 返回用户态并调用 `mmap`**：
    B 被调度执行后，一路从内核栈返回到了用户态。B 执行了你的代码：`mmap(addr=0, length=4096...)`。陷入内核。
    **7. sys_mmap 的“虚空画饼”（Lazy Allocation）**：
    内核进入 B 的 `sys_mmap` 函数。内核在 B 的虚拟空间高处找到了一个空地（比如虚拟地址 `0x6000`），并在 B 的 **VMA 账本（`proc[6].vmas`）** 中登记：
    • `v->addr = 0x6000`, `v->length = 4096`。
    • **注意！此时没有任何物理内存被分配！B 的页表里虚拟页 `0x06` 依然是无效的（PTE_V = 0）。**
    内核直接把 `0x6000` 这个字符串当做返回值丢给用户态的 B。
    **8. B 触雷（Page Fault 缺页中断）**：
    B 回到用户态，兴奋地执行了一句 `p[0] = 'X'`（试图向虚拟地址 `0x6000` 写数据）。
    MMU 拦截：查 B 的页表（SATP=`0x80002000`），发现第 `0x06` 项是空的！MMU 立刻向 CPU 抛出异常（Page Fault）。B 再次被迫陷入内核态。
    **9. 内核填坑（分配物理页）**：
    内核的 `usertrap` 捕捉到了缺页异常，读取 `stval` 寄存器，发现惹祸的虚拟地址是 `0x6000`。
    内核去查 B 的 VMA 账本，发现 `0x6000` 确实是刚才 `mmap` 登记过的合法范围！
    于是，内核：
    • 从空闲物理内存池中找出一页，物理地址为 **`0x03F00000`**。
    • 调用文件系统接口，把底层文件的 4KB 数据读进物理页 `0x03F00000`。
    • **修改 B 的页表**：把虚拟页 `0x06` 映射到物理页框 `0x3F00`，设置标志位 `PTE_V=1`。
    **10. 时空倒流（重试指令）**：
    坑填好了，内核执行 `sret` 返回用户态。硬件自动**重新执行**刚才失败的那句 `p[0] = 'X'`。
    这一次，MMU 查表顺利通过，将 `0x6000` 翻译为真实的物理地址 `0x03F00000`，字母 'X' 被完美地写进了真实的内存条中。

    # 操作系统底层概念对照表：RISC-V (xv6) vs x86 (Linux)
    
    ## 一、 核心硬件寄存器与指令对照 (Architecture Level)
    
    这些是 CPU 硬件层面的概念，操作系统的底层汇编代码必须和这些硬件打交道。
    
    | 概念描述 | RISC-V 体系结构 | x86 / x86-64 体系结构 | 核心作用说明 |
    | --- | --- | --- | --- |
    | **页表基址寄存器** | `satp` (Supervisor Address Translation & Protection) | `CR3` (Control Register 3) | 存放当前进程的**顶级页表物理地址**。每次进程切换时必须重写此寄存器，MMU 凭它进行地址翻译。 |
    | **中断向量表入口** | `stvec` (Supervisor Trap Vector) | `IDTR` (Interrupt Descriptor Table Register) | 告诉 CPU：发生中断/异常时，操作系统的“应急处理大门”（入口函数地址）开在哪里。 |
    | **触发系统调用** | `ecall` (Environment Call) | `int 0x80` (旧) / `syscall` (64位) / `sysenter` | 用户态程序主动触发陷阱（Trap），要求 CPU 提升特权级并跳入内核态。 |
    | **中断/陷阱返回** | `sret` (Supervisor Return) | `iret` / `sysret` | 内核处理完毕，降级回用户态，并恢复用户程序的执行流。 |
    | **缺页异常地址存放** | `stval` (Supervisor Trap Value) | `CR2` (Control Register 2) | 当发生 Page Fault（缺页异常）时，硬件会自动把“惹祸的那个虚拟地址”存放在这里，供 OS 读取填坑。 |
    | **保存断点地址** | `sepc` (Supervisor Exception PC) | 硬件自动压入内核栈 (EIP/RIP) | 发生中断的一瞬间，硬件保存当前被打断的指令地址，以便将来返回时继续执行。 |
    | **特权级分类** | U-Mode (用户), S-Mode (内核), M-Mode (机器) | Ring 3 (用户态), Ring 0 (内核态) | 划定权限边界。系统调用就是从 U-Mode 切到 S-Mode，或者 Ring 3 切到 Ring 0。 |

    ## 二、 操作系统软件数据结构对照 (OS Software Level)
    
    这些是操作系统内核用 C 语言写出来的数据结构，体现了不同系统的设计复杂度。
    
    | 概念描述 | xv6 操作系统 (极简教学版) | Linux 操作系统 (工业生产版) | 核心作用说明 |
    | --- | --- | --- | --- |
    | **进程控制块 (PCB)** | `struct proc` | `struct task_struct` | 进程的“绝密档案”，记录进程状态、PID、打开的文件等所有元数据。 |
    | **虚拟内存管理 (大管家)** | `pagetable_t pagetable` (直接挂在 proc 下) | `struct mm_struct` | 统领整个进程的虚拟地址空间。在 Linux 中它负责连接硬件（pgd）和软件（mmap链表）。 |
    | **虚拟内存区域 (地皮)** | `struct vma` 数组 (固定大小，如 16 个) | `struct vm_area_struct` 链表/红黑树 | 记录用户空间的一块块“地皮”（如代码段、mmap 映射区）的起始地址和读写权限。 |
    | **用户态现场保存区** | `struct trapframe` (单独分配一页物理内存) | `struct pt_regs` (直接压在内核栈顶) | 进出内核时，保存用户程序的 32 个通用寄存器。Linux 做法更紧凑，直接利用内核栈。 |
    | **内核态上下文切换** | `struct context` (存在 proc 中) | `struct thread_struct` (存在 task_struct 中) | 当内核决定把 CPU 交给别人时，保存内核当前的调用栈指针（SP）和返回地址等。 |
    | **文件描述符表** | `struct file *ofile[NOFILE]` | `struct files_struct *files` | 记录进程打开了哪些文件。Linux 做成了独立的结构体以便在多线程间共享。 |

    这里的Private小块指的是P1和P2共享的若干虚拟页（P2会得到一个完全不同的一级页表基址，这个一级），它们映射在Physical memory的真实物理页上。fork时，这些页的权限，在页表上被标识为只读（这样下次写的时候会触发缺页），而fork时，P2会得到与P1完全一样的对应这些页的VMA结构体（比方说这个VMA表示的是.text段），并且把这些vma中的flags改为private COW。P2下次写其中一页时（黄色块代表最少一页），MMU找到这一物理页的权限是只读，触发缺页异常，内核从vma链表中找到这个虚拟地址对应的(vm_start, vm_end)段，一看其实是写时复制，于是分配一个新的物理页给P2这次写操作，并且把这个新的物理页设置为可读可写。
    
    虽然页表基址不一样，而且P1和P2也会有完全不重叠的物理空间上的两组多级页表，但是由于共享虚拟地址，它们的寻址逻辑实际上是一样的，只是一开始找的第一级页表的物理位置不一样，导致他们后续找到的页表物理位置也不一样，但虚拟地址决定着每个页表中要找的索引是一样的。所以实际上，P1和P2的前几级每个页表物理地址不一样，存的条目（指向下一级页表地址）也不一样，只有最后一级页表，他们存的条目是一样的（共享物理页）。
